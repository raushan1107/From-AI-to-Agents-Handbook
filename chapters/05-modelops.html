Model Choice, Evaluation and Deployment

A model demo proves that something can work once. Evaluation helps establish whether it works reliably for your users.

Connect the concept

Evaluation begins with a task definition and representative dataset. Include ordinary cases, edge cases, ambiguity, unsafe requests, unsupported questions and cases where the correct response is to ask or refuse. Keep a final holdout set separate from examples used to tune prompts.

Measure correctness or task success, groundedness, relevance, completeness, safety, latency, throughput and cost. Human review matters for subjective quality. Automated graders are useful proxies, not ground truth; inspect example-level failures and calibrate graders.

Compare models under the same prompt, tools, data and settings. Record exact model/deployment version and test date. A quality winner may be too costly, slow or unavailable in a target region. After release, monitor drift, failures, token use, latency, retrieval health and tool errors.

Re-run evaluation after changes to the model, prompt, retrieval pipeline or tools. Optimization without quality checks can make a system cheaper while making it worse.

Evaluation is a measurement loop

Evaluation is like a driving test on varied roads, not one lap in an empty lot. A test set should represent real routes and difficult conditions. A holdout set is a sealed final route that you do not use to tune the system.

Track each failure by severity and cause. Aggregate scores summarize; examples explain what to fix.

Hands-on lab: evaluate a model against a small test set

Prerequisites

Use your own Foundry project, model deployment and permission to run evaluations. Evaluator models consume tokens and may incur charges; consult Microsoft Learn for required roles.

  1. Create a local CSV with columns appropriate to the evaluation flow, such as query, context and ground_truth. Add 8–12 fictional Northstar cases: a straightforward policy question, missing evidence, conflicting dates, an irrelevant request, and an instruction asking for a prohibited promise. Never upload private customer data.
  2. For each case, record the model’s response using the same prompt, model deployment and settings. Keep a copy of the exact prompt and date so the run can be reproduced.
  3. In Foundry, open Evaluation and start an evaluation for the model or dataset. Upload the CSV, map the input and expected-answer fields, and select evaluators that match your task. If AI-assisted quality evaluators are selected, configure the required evaluator model.
  4. Review every field mapping before submitting. Name the run with a version such as northstar-prompt-v1 and submit.
  5. Open the completed run. Inspect aggregate scores and individual examples. Read failures instead of relying on the average: a high mean can hide a serious failure on a rare but important case.
  6. Change one prompt element, rerun the same cases and compare results. Do not tune repeatedly against the only test set; keep some cases held out for a final check.
  7. Record quality, refusal behavior, latency and token consumption. Choose an acceptance threshold before deciding which version wins.

Expected result

A named evaluation run with aggregate and per-example results; inspect failures and compare against a holdout set.

Cleanup

Remove temporary datasets and evaluator deployments according to your retention policy.

Trainer's takeaway

Define success in advance, preserve holdout cases, inspect individual failures and rerun evaluation after every material change.
