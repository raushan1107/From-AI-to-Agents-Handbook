Part III

Knowledge-Enhanced Agents and Orchestration

Agents become useful when they can combine reasoning with trusted information and bounded actions.

In this chapterStart hereConnect the conceptConcept mapGrounded knowledge labMulti-agent labTrainer's takeawayQuick check

Let's make sense of it

An agent can use a retrieval tool to search manuals, a database tool to check an order and a ticket tool to create a support case. The model decides which supported capability may help; the application enforces access and business rules.

Connect the concept

Orchestration is the control flow around model calls and tools: which step runs, what information it receives, what can run in parallel, and what happens when a step fails. A workflow makes that control flow inspectable instead of leaving every choice to an open-ended prompt.

Choose a pattern by the dependency between steps

PatternGood fitCost or risk to manage
Sequential pipelineEach stage needs the prior result, such as extract → verify → summarize.Latency adds across stages; a bad early result can propagate.
Concurrent fan-out / fan-inIndependent lookups or checks can run at the same time.Needs a merge rule, timeout policy and handling for partial results.
Handoff / routingA request should move to one specialist or ask a person for missing information.Routing loops and lost context need explicit limits.
Supervisor with workersA coordinator must decompose a task and decide which specialists to call.More model calls, coordination complexity, disagreement and higher cost.
Group discussionSeveral perspectives are useful and a bounded turn-taking rule exists.Can loop or produce long debate without a stopping condition.

For example, a support case could retrieve policy and order history concurrently, then have one response step reconcile both. If the policy result determines which order data is allowed to be retrieved, use a sequence instead. Add a second agent only when evaluation shows a meaningful improvement over one agent with well-scoped tools.

Conversation history, task state and memory are different

  • Conversation history is the recent exchange needed to answer the next turn. It may be truncated or summarized as it grows.
  • Task state is structured progress for one job: selected document, approval status, retry count or current workflow step. Store it explicitly so a restart does not depend on reconstructing it from prose.
  • Durable memory is a small, approved fact intended to help in future sessions, such as a user-selected language preference. It needs a source, owner, purpose, retention rule and a way to correct or delete it.

Analogy: conversation history is the scratchpad on today’s desk, task state is the checklist for this particular case, and durable memory is a labeled note filed for later. Do not file sensitive or inferred claims just because they appeared in a chat. Scope memory by user and tenant, retrieve only what the request needs, and apply normal authorization checks to every connected data source.

Knowledge sources differ in freshness and authority. Retrieval finds passages in an index; a database or API can return current records; conversation history captures what was said. Keep provenance, retrieval time and authorization identity. Set timeouts, bounded retries, explicit failure messages and human escalation routes.

Orchestration is choosing the next bounded step

Think of orchestration as a coordinator deciding whether to consult a policy specialist, an order system, or both. Concurrent work helps only when those tasks are independent; a sequential workflow is clearer when step two depends on step one.

A multi-agent design is justified by measured gains, not by the number of roles in the diagram.

Hands-on lab: connect an agent to grounded knowledge

Prerequisites

You need a Foundry project, an Azure AI Search connection/index from the retrieval exercise, and permission to create agents and configure connections. Model/search resources may incur charges.

  1. In Microsoft Foundry, open the project and choose Build → Agents. Create a prompt agent with a chat model deployment.
  2. Set instructions: Answer policy questions only from the connected search results. If the results do not support an answer, say that the available documents do not answer it. Include the source citation returned by the search tool. Do not make account changes or promise an outcome.
  3. Open the agent’s knowledge/tool configuration and add Azure AI Search. Select the existing project connection and index. Use the documented authentication method; for keyless access, configure managed identity and only the required Search roles.
  4. Save a version and test: What does the late-delivery policy say about review? Inspect the answer and citation, then open the cited document to verify the passage really supports the answer.
  5. Ask a question that combines two policy clauses and then one question absent from the documents. Check whether the agent combines evidence accurately and admits when evidence is missing.
  6. Repeat with a question that requests a personal order status. The policy index does not contain a live order record, so the agent should not imply that it checked one.
  7. Review traces or tool activity if available. Note the retrieved query, documents and returned citations. Poor retrieval needs an index/query fix; unsupported prose needs prompt or model evaluation.

Expected result

The agent returns answers with source citations, admits when its index lacks evidence and does not claim access to live order data.

Cleanup

Delete the test agent and only delete Search resources if they are dedicated to this exercise.

Hands-on lab: build a two-step agent workflow

This small Python exercise sends a fictional policy question through a reader and an evidence reviewer. It uses a sequential workflow so you can observe how one agent’s output becomes the next agent’s input. It does not create or modify business records.

Prerequisites

A Microsoft Foundry project with an available chat model deployment, Python 3.11+, Azure CLI, and permission to use the project. Costs can apply to model calls. Sign in with your own authorized account; this guide supplies no credentials.

Prepare the environment

  1. In Microsoft Foundry, open or create a project and deploy a chat model. Copy the project endpoint and deployment name from the project/model details pages.
  2. Install the Azure CLI and Python 3.11 or later. Sign in with az login, selecting the tenant and subscription that contain the project.
  3. Create and activate a virtual environment, then install the official framework packages:
    python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# macOS/Linux: source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install agent-framework-foundry
  4. Set environment variables in the same terminal. Replace the example values with your project endpoint and exact deployment name:
    $env:FOUNDRY_PROJECT_ENDPOINT = "https://YOUR-RESOURCE.services.ai.azure.com/api/projects/YOUR-PROJECT"
$env:FOUNDRY_MODEL = "YOUR-DEPLOYMENT-NAME"
    For macOS/Linux use export FOUNDRY_PROJECT_ENDPOINT="..." and export FOUNDRY_MODEL="...".
  5. Save the following as workflow_demo.py and run python workflow_demo.py:
import asyncio
import os

from agent_framework.foundry import FoundryChatClient
from agent_framework.orchestrations import SequentialBuilder
from azure.identity import AzureCliCredential


async def main():
    client = FoundryChatClient(
        project_endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],
        model=os.environ["FOUNDRY_MODEL"],
        credential=AzureCliCredential(),
    )

    reader = client.as_agent(
        name="policy_reader",
        instructions=(
            "Use only the fictional policy in the user's message. "
            "Extract the stated rule. If it is absent, say so."
        ),
    )
    reviewer = client.as_agent(
        name="evidence_reviewer",
        instructions=(
            "Check the previous answer against the fictional policy in the request. "
            "Remove unsupported claims and return a concise corrected answer."
        ),
    )

    workflow = SequentialBuilder(
        participants=[reader, reviewer],
        chain_only_agent_responses=True,
    ).build()

    result = await workflow.run(
        "Fictional policy: Late deliveries can be reviewed within 14 days "
        "of delivery. The review does not guarantee a refund. "
        "Question: Can a late delivery be reviewed, and is a refund guaranteed?"
    )
    for output in result.get_outputs():
        for message in output.messages:
            print(message.text)


if __name__ == "__main__":
    asyncio.run(main())

Inspect the behavior

  1. Run it once. The answer should say review is possible within 14 days and a refund is not guaranteed.
  2. Change the fictional policy and question. Check that the reviewer removes claims unsupported by the changed policy.
  3. Temporarily reverse the participant order and observe why workflow order matters; then restore reader → reviewer.
  4. Try a one-agent baseline with the same instructions. Compare factual accuracy, latency and token usage. A second agent is useful only if the measured quality gain justifies its extra call.

Expected result and cleanup

The terminal prints the final reviewer response. The workflow has no durable memory: each run is independent. Stop the script and deactivate the virtual environment when finished. Review model usage in the Foundry project; remove any dedicated deployment or resources only if they were created solely for this exercise.

Trainer's takeaway

Start with one agent. Add orchestration only when evaluation justifies the extra latency, cost and failure paths.
