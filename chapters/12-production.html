Part IV

Putting It All Together: Production AI

A production AI system is a software system with probabilistic components. It needs the same engineering discipline as any other important application—and additional controls for model behaviour.

In this chapterStart hereConnect the conceptPlan the solutionTracing labConcept mapHands-on labTrainer's takeawayQuick check

Let's make sense of it

A typical architecture includes a user interface, identity layer, application API, orchestration service, model endpoint, retrieval index, business tools, content safety controls, telemetry and data stores. Not every solution needs every component. Choose based on the risk and workload.

Connect the concept

A production system may include a client, identity layer, application API, orchestration, model deployment, search index, business tools, content safety, telemetry and data stores. Choose infrastructure and deployment type for workload, latency, throughput, residency, networking and cost needs.

Security includes least privilege, managed identity/keyless auth, secret management, role policies, private networking where required, data protection and tenant isolation. Enforce tool permissions outside the model. Audit provenance and approvals while redacting sensitive telemetry.

Responsible AI spans harm mapping, measurement, mitigations, moderation, user transparency, human oversight and incident handling. Monitor model quality and drift as well as infrastructure health; observe traces, token use, safety events, latency and tool/search failures.

Use quotas, rate limits, budgets, capacity plans, staged releases, CI/CD, versioned prompts and rollback. The best system is the simplest architecture that meets its safety and service objectives.

Plan the service before choosing a model

Start with the user outcome and the consequences of failure. Then select the smallest suitable capability: a small language model or task-specific Foundry Tool may handle a narrow task; a larger model may be needed for complex synthesis; a multimodal model is needed for image/audio/video input; search or a knowledge service supplies current content; an agent runtime coordinates tool use.

Plan costs for model input/output tokens, fine-tuned model hosting, agent tools, search tier, storage, telemetry ingestion and retention. A service with a low per-call price can still be expensive when context is large, retries multiply, or hosted sessions remain active.

For security, prefer Microsoft Entra and managed identity to long-lived application keys when supported. Scope role assignments to the necessary resource, use private networking when the data boundary requires it, and test permissions with the actual application identity. Do not treat a private endpoint as a substitute for authorization.

For change management, version prompts, tool schemas, data/index configuration, model deployment and evaluation cases. CI/CD should run static checks, evaluation and safety gates before deployment, then a smoke test and gradual rollout. Keep a known-good version for rollback. See the current Foundry CI/CD guidance for hosted agents.

Hands-on lab: inspect an agent trace in Foundry

Goal: follow a fictional request through model and tool steps, then set one monitoring action. Use synthetic content only.

Prerequisites and privacy

You need your own Foundry project and an agent from Chapter 07 or 09, permission to connect Application Insights, and Log Analytics Reader access to query traces. Application Insights may incur ingestion and retention charges. Traces can capture prompts, outputs and tool results; keep sensitive content out and follow your organization’s retention policy. See Microsoft’s Foundry tracing guide.

  1. Open the Foundry project. Select Build → Agents → Traces, then choose Connect. Create a dedicated Application Insights resource for this lab or connect an approved existing resource. If the button is not present, use Manage → Project details → Connected resources.
  2. Invoke a safe test question that requires one retrieval or read-only tool call. Do not use an order ID tied to a real person. Wait a few minutes for telemetry ingestion.
  3. Return to Traces and open the request. Follow the spans through the agent, model call, search/tool operation and response. Record end-to-end latency, slowest step, token usage, tool errors and whether retrieved evidence supported the answer.
  4. Run a second request with missing evidence. Check whether the agent refuses or asks for a clarification. Compare the trace and response to your expected behavior.
  5. Write one alert or review rule: for example, a rise in tool errors triggers investigation; a grounding failure triggers evaluation; high latency leads to a capacity review. Name an owner and an action, rather than collecting metrics without a response plan.
  6. Review who can query traces. Restrict access because telemetry may contain prompt and output content. Disable or minimize sensitive content recording where your configuration allows it; redact before telemetry is emitted.

Expected result

You should be able to locate the model and tool stages in a request and identify an operational action from observed data. Tracing explains a request; evaluation measures its quality across a dataset. Use both.

Cleanup

Remove the test agent and disconnect or delete a dedicated Application Insights resource when finished. Do not delete a shared telemetry resource. Review its retention and access settings.

Production quality is an end-to-end property

Think of production AI like an airport: the plane matters, but identity checks, routing, safety systems, control-room monitoring and fallback procedures make the service dependable.

The model is one component. The application owns security boundaries, safe tool execution, retention, rollback and accountability.

Hands-on lab: create a production readiness review

Prerequisites

No subscription is needed for the core design review. Optional monitoring requires your own Azure subscription, Application Insights resource and permission to send telemetry.

  1. Draw the request path: user interface → identity check → application API → retrieval service → model → answer and citations. Add an order-status tool only if the exercise needs live account data.
  2. For each component, name the identity used, the minimum permission required, and what data it can read or change. Mark where retrieved text and model output are untrusted.
  3. Define three nonfunctional limits: maximum response time, maximum tool calls per turn and a cost/token budget. Decide what the application does if retrieval or the model is unavailable.
  4. Write five release checks: answer quality on a held-out dataset, citations point to supporting passages, users cannot retrieve unauthorized content, tool arguments are validated, and logs omit sensitive content.
  5. Define monitoring signals for request volume, errors, latency, model tokens, retrieval failures, tool rejections and user feedback. Assign an owner and an action for each threshold.
  6. Plan a gradual release: test environment, small pilot group, review metrics, expand only if thresholds pass, and rollback to a known version if quality or safety falls.
  7. Optional Azure practice: create an Application Insights resource in a dedicated resource group. Follow the current Azure Monitor OpenTelemetry guide for your application language; send a few synthetic requests and confirm telemetry appears in the Azure portal. Use environment configuration for connection details and never commit secrets.

Expected result

A one-page system diagram and release checklist with named owners, limits, monitoring thresholds and rollback actions.

Cleanup

Remove synthetic logs and dedicated Application Insights resources according to retention policy; avoid deleting shared telemetry.

Trainer's takeaway

Production readiness covers security, evaluation, monitoring, fallback, budgets, responsible AI and accountable operations.
