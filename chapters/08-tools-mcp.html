Part III

Tools, APIs, Function Calling and MCP

A model can describe an action. To perform it, it needs a controlled connection to software that can do the work.

In this chapterStart hereConnect the conceptFoundry toolsTool demoConcept mapHands-on labTrainer's takeawayQuick check

Let's make sense of it

An API is a defined interface through which software requests data or actions. A tool wraps an operation in a form the model-driven application can expose, such as search policy, create ticket or check order status.

Connect the concept

An API is an interface for software requests. Function calling exposes a name, description and argument schema; the model may return a structured request, but host code validates it, checks identity and permission, invokes the API, and returns a bounded result.

MCP standardizes how a host/client connects to servers that expose tools, resources or prompts. It complements APIs and does not grant safe access by itself. The host decides which servers to trust and which capabilities to expose.

Use allow-lists, schema validation, authentication, least privilege, timeouts, output limits and audit trails. Treat tool descriptions and results as untrusted input. Separate preparing a consequential action from committing it, with human approval where appropriate.

Choose the right tool for the job

Tool names describe different execution boundaries. “The model can use a tool” does not mean every tool is the same or that a model has direct account access.

Availability depends on the model, endpoint/API, project region and current product configuration. For example, hosted File Search and Code Interpreter are available through Responses-style flows, while Chat Completions has a different capability set. Check Microsoft’s runtime components and tool-specific guidance before building around one.

Map a customer request to tools

For “Summarize these 30 fictional tickets and show weekly trends,” Code Interpreter can analyze a provided CSV. For “What does our shipping policy say?”, File Search or Azure AI Search can retrieve a policy. For “What is the latest public API change?”, Web Search can find online sources. For “Check this signed-in customer’s order,” a narrowly scoped function can call the business API after identity and authorization checks.

Use a deterministic calculation in code when exact results matter. Use hosted code execution for bounded analysis of user-provided files. Use search to locate evidence. Use a function only for a defined application capability. The application remains responsible for access control in every case.

Hands-on lab: compare hosted tools with a fictional CSV

Goal: use a sandboxed analysis tool and compare it with document search, while observing that the model’s tool choice and answer need verification.

Prerequisites and cost

You need your own Azure subscription, Foundry project, a supported model deployment, and permission to create/run an agent. Code Interpreter availability varies by region and model and has charges beyond model tokens. A session can stay active for up to an hour with an idle timeout. No credentials are supplied. Review the current Code Interpreter guide and toolbox guide.

  1. Create a local CSV named weekly_support.csv with only synthetic data:
    week,late,returned
2026-01-05,12,3
2026-01-12,9,4
2026-01-19,15,2
  2. In Microsoft Foundry, open the project and create a prompt agent. In its tools configuration, add Code Interpreter. Save a version.
  3. Upload the synthetic CSV when the playground requests files. Ask: Calculate total late and returned cases, show the weekly late-case trend, and create a bar chart. State which columns you used.
  4. Check the arithmetic manually: late cases total 36; returned cases total 9. Compare the chart labels and totals to the CSV. A generated plot is not correct merely because it looks polished.
  5. For a separate experiment, create a new agent/version with File Search if available. Upload a short fictional policy document and ask a question answered by one paragraph. Open the supporting passage and check any citation.
  6. If Web Search is available, try a harmless current question and inspect the sources. Do not include confidential content in a web query. A source link is not proof that the generated summary accurately reflects the page.
  7. Record which tool ran, what input it received, what result came back, and what you independently checked. Do not combine a broad tool with account-changing access.

Expected result

You should distinguish computation over a supplied file, retrieval over uploaded documents and public web lookup. The tool output becomes model context; validate it and enforce data permissions outside the model.

Cleanup

Delete the test agent, uploaded file, conversation and any vector store created only for the exercise. Delete an exercise-only deployment when finished and check billing for active sessions.

Tool calling separates intent from authority

A model tool request is a request slip at a service desk. The clerk—not the slip—checks identity, required fields and authority, then calls an approved system. MCP is a standardized connector pattern for exposing capabilities, not an authorization layer.

Read-only tools, reversible actions and high-impact actions need different controls.

Hands-on lab: build and run a safe tool boundary

Prerequisites

Python 3.10+ for the local demo; no Azure account is needed for that exercise. A separate Foundry tools exercise needs your subscription, project, eligible deployment and tool permissions; some tools incur additional charges.

  1. Create a file named tool_demo.py and paste the complete code below.
  2. Open a terminal in that folder and run python tool_demo.py (on some systems use python3 tool_demo.py).
  3. Observe the valid read-only request return a result. Then observe the oversized amount and unknown tool being rejected before any operation runs.
  4. Edit the request list to try a missing order ID, a negative amount and a string where a number is expected. Add validation tests before adding any new capability.
from decimal import Decimal

ORDERS = {"NS-1042": {"status": "delayed", "amount": Decimal("24.50")}}


def check_order(order_id: str) -> dict:
    if not isinstance(order_id, str) or order_id not in ORDERS:
        raise ValueError("Unknown order")
    return ORDERS[order_id]


def request_refund_review(order_id: str, amount: Decimal) -> dict:
    # Demo only: return a proposed review; never issue money.
    if order_id not in ORDERS:
        raise ValueError("Unknown order")
    if amount <= 0 or amount > ORDERS[order_id]["amount"]:
        raise ValueError("Amount outside the allowed range")
    return {"status": "review_requested", "order_id": order_id,
            "amount": str(amount), "human_approval_required": True}


TOOLS = {"check_order": check_order,
         "request_refund_review": request_refund_review}


def dispatch(proposal: dict) -> dict:
    name = proposal.get("name")
    args = proposal.get("arguments", {})
    if name not in TOOLS:
        raise ValueError("Tool is not allow-listed")
    if not isinstance(args, dict):
        raise ValueError("Arguments must be an object")
    if name == "check_order":
        return TOOLS[name](args.get("order_id"))
    if name == "request_refund_review":
        return TOOLS[name](args.get("order_id"), Decimal(str(args.get("amount"))))
    raise ValueError("No validated handler exists")


if __name__ == "__main__":
    examples = [
        {"name": "check_order", "arguments": {"order_id": "NS-1042"}},
        {"name": "request_refund_review", "arguments":
         {"order_id": "NS-1042", "amount": "99.00"}},
        {"name": "delete_all_orders", "arguments": {}},
    ]
    for item in examples:
        try:
            print(item["name"], "->", dispatch(item))
        except Exception as exc:
            print(item["name"], "REJECTED ->", exc)

Expected result

The local code accepts a valid read-only request and rejects invalid requests. The optional Foundry exercise lets you inspect hosted tool calls and results.
