How We Reached Large Language Models

To understand an LLM, follow the path from words to tokens, from tokens to vectors, and from vectors to attention.

Let's make sense of it

Computers do not directly process words as human meanings. Text is split into tokens—often word pieces, punctuation or other units. Each token is mapped to a numerical representation. An embedding is a learned vector that helps represent relationships and context in a model’s mathematical space.

Connect the concept

Tokenizers split text into tokens, which may be words, word pieces or punctuation. The model maps token IDs to vectors and adds positional information. Contextual layers update each token representation using information from other tokens in the sequence.

Self-attention compares query and key projections to estimate which tokens are relevant, then combines value projections. Multiple attention heads learn different relationship patterns in parallel. They are learned mathematical operations, not literal questions or a factual database.

Many language models are pretrained by predicting the next token repeatedly. Instruction tuning and preference or safety training can then shape response behavior. At inference, the model generates one token at a time conditioned on context and prior output, which explains both fluency and possible fabrication.

Tokens are not words, the context window is finite, and embeddings are vectors rather than definitions. Retrieval and tools can supply evidence, but the application must still validate results.

From text to a prediction: the model’s working path

Think of attention as a reading group that passes notes about which words clarify which other words. In “The package was late because it missed the depot,” context links “it” to “package.” This analogy helps explain relevance weights, but the model calculates learned vector operations, not human interpretations.

A final probability distribution scores candidate next tokens. Decoding selects one, appends it to the context, and repeats. The next-token objective teaches statistical patterns, not a guarantee that every generated statement is checked.

Hands-on lab: observe token generation in the Foundry chat playground

Prerequisites

Use your own Azure subscription, Foundry project and permission to use a deployed chat model. Inference may consume quota and incur charges; reuse an existing deployment where possible.

  1. Sign in to Microsoft Foundry and open your project. Choose Build → Models, select an available chat model and deploy with a supported default configuration if the project has no deployment.
  2. Open Playgrounds → Chat playground and select the deployment. Enter this system instruction: You are a careful Northstar support assistant. Answer in one short sentence. If a policy fact is not supplied, say what information is missing.
  3. Ask: A customer asks whether an order placed yesterday is refundable. The policy text was not provided. What should you say? Note that a well-instructed assistant should not invent the policy.
  4. Now provide a short policy paragraph in the user message and ask the same question. Observe how the additional context changes the continuation.
  5. Keep the prompt fixed and compare the available sampling settings, changing only one control at a time. Record the setting, output and whether the answer followed the constraint. Do not assume lower variation guarantees factual accuracy.
  6. Try an ambiguous prompt and a prompt with irrelevant text. Note where the answer becomes uncertain or ignores information.

Expected result

Observe how tokenized context conditions a sequence of generated tokens; compare a prompt with and without supplied policy evidence.

Cleanup

Remove personal data from prompts and delete a deployment created only for this lab if it is no longer needed.

Trainer's takeaway

Trace text through tokens, vectors, attention and next-token prediction; fluent output is not proof of a fact lookup.
