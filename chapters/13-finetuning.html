Fine-tuning: Teaching a Model a More Consistent Pattern

Fine-tuning adapts a supported base model using task-specific examples or preferences. It can shape how a model responds; it is not a shortcut for fresh facts, secure permissions or careful evaluation.

What fine-tuning changes

Imagine onboarding a new teammate. A prompt is the shift briefing, retrieval is the reference shelf, and fine-tuning is repeated coached practice that helps the teammate follow a recurring response pattern. The analogy has a limit: a fine-tuned model adjusts learned parameters; it does not acquire human understanding or guaranteed recall.

A foundation model is trained broadly before an application uses it. Fine-tuning continues training from an eligible base model with a curated dataset for a narrower behavior: for example, consistently classifying support messages into a fixed taxonomy or producing a domain-specific response format.

Fine-tuning is usually a poor first response to missing or changing knowledge. If refund rules change each month, retrieve the current policy at request time. If the model should always emit a schema or use a particular tone, examples may help. If you need a deterministic rule, implement and test that rule in application code.

These methods are not interchangeable buttons. Model, region, training method and account eligibility determine what the portal offers. Some methods or models may be preview, gated or unavailable in a region. Follow the current Microsoft Foundry fine-tuning guide before preparing a dataset.

Prompt engineering, retrieval and fine-tuning solve different problems

  • Prompting: change instructions, examples or parameters to improve how the model handles the current task. Fast to iterate, but the prompt consumes context and does not guarantee rule enforcement.
  • Retrieval (RAG): provide current, sourced information at request time. Best when answers depend on changing or private documents. Retrieval permissions and citation quality still need engineering.
  • Fine-tuning: adapt response patterns from many examples. Best when behavior is repeatedly inconsistent despite clear prompts, and you have enough clean examples to teach and evaluate the desired pattern.
  • Code and workflow: enforce exact rules, calculations, authorization and step order deterministically.

These can be combined. A tuned model can format a grounded answer consistently, while application code checks access and business rules. Evaluate the complete system rather than assuming the tuned model is better in isolation.

Build a dataset that teaches the right behavior

A dataset is a specification in example form. Each row says, “for this kind of input, this is the behavior we want.” Poor examples teach poor behavior very efficiently.

  • Write examples that cover normal requests, edge cases, ambiguity, out-of-scope questions and appropriate refusals.
  • Use data you are allowed to use. Remove personal data and secrets; verify ownership and licensing; avoid putting confidential customer records into a training file.
  • Keep training, validation and final test examples separate. Near-duplicates leaking across these sets make evaluation falsely optimistic.
  • Keep examples consistent with one another. Conflicting target answers create an unstable training signal.
  • Review label quality and class balance. A large but noisy dataset is not automatically useful.

For SFT, a chat example is often represented as one JSON object per line. A minimal illustrative line is:

{"messages":[{"role":"system","content":"Classify Northstar messages using only these labels: delivery, billing, account."},{"role":"user","content":"My replacement order has not arrived."},{"role":"assistant","content":"delivery"}]}

That line demonstrates structure only; it is not a complete training dataset. Requirements for file format, minimum examples, model, and fields vary. Check the selected model’s current validation rules in the portal and official docs.

Hands-on lab: decide whether SFT improves a support classifier

Goal: design and, if your environment offers an eligible model, run a small supervised fine-tuning experiment for consistent category labels. The comparison with the untuned baseline is the core exercise.

Prerequisites, permissions and cost

You need your own Azure subscription, Microsoft Foundry project, an SFT-eligible model in a supported region, Foundry User access to train, and a role that permits deployment if you choose to deploy. Training, evaluation and a deployed endpoint can incur charges; deployed fine-tuned models can have hourly hosting costs. This book supplies no credentials. Confirm current model and dataset requirements in the fine-tuning guide; availability changes.

  1. Define a narrow task: label each fictional support message as delivery, billing, or account. Decide how ambiguous messages should be handled before collecting examples.
  2. Create a JSONL training file with many distinct, reviewed examples, one JSON object per line using the supported chat format. Create a separate validation JSONL file with unseen examples. Do not copy the illustrative single line as your dataset.
  3. Before training, use the same holdout examples to test the base deployment with a prompt-only baseline. Record exact-match accuracy, invalid labels, and how it handles ambiguity. Keep the final test set untouched.
  4. In Microsoft Foundry, select your project and open Build → Fine-tune → Fine-tune. Select an eligible base model and Supervised fine-tuning. Upload the training and validation files; inspect the preview and resolve validation errors.
  5. For the first run, keep supported hyperparameters at their defaults. Name the run clearly and submit. Monitor status and validation metrics; cancel if the job is failing or learning from malformed data.
  6. When complete, compare training and validation trends. If training improves while validation worsens, suspect overfitting. Do not infer quality from a single training loss number.
  7. If the results meet your prewritten acceptance criteria, deploy the fine-tuned model and rerun the same holdout evaluation against the base model. Deployment is optional and may create ongoing hourly cost. Compare quality, latency, throughput and total cost.
  8. Record the model/version, dataset version, training settings, evaluator and result. Keep a rollback path to the base deployment.

Expected result

You should finish with a justified decision: fine-tune, improve the examples, keep prompt-only, use retrieval, or enforce the rule in code. “The training job succeeded” is not the same as “the application improved.”

Cleanup

Delete an exercise-only deployment promptly when comparison is complete. Remove uploaded datasets, agents and resource groups only if they were created solely for this lab and no one else depends on them. Retain approved evaluation records according to your data policy.
